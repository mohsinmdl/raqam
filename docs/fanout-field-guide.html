Claude Code · Orchestration

Fan-Out Field Guide

Six ways to run more than one thing at once inside a Claude Code session — and, just as important, how to tell them apart so you reach for the right one.

For: getting fluent, not shipping Covers: Agent · SDD · Workflow · Task · Goal · Loop Read: ~7 min

The one idea to hold onto

Two columns, pick one from each

Every technique below answers one of two questions. How wide does the work spread? — one worker, several, or many. And what tells it to keep going? — a background job, a condition, or a clock. The first three are ways to fan out; the last three are drivers that decide when work stops. You almost always combine one of each.

Family Technique In one line You trigger it with
Fan-out Agent One subagent with its own context does one job and reports back. “use a subagent to…”
Fan-out SDD One subagent per plan task, reviewed between each. “execute this with SDD”
Fan-out Workflow A JavaScript program orchestrating many subagents deterministically. ultracode … / /effort ultracode
Driver Task Background execution + a progress checklist. (automatic) · plain language
Driver Goal Keep working until a stated condition becomes true. /goal <condition>
Driver Loop Re-run on an interval, or at a pace Claude picks. /loop [interval] [prompt]

Family one · ways to fan out

Spreading the work

Fan-out · one worker Agent

Agent — a subagent you hand one job

A fresh Claude with its own context window, system prompt, and tools. It works, then returns a final report your main session relays to you.

What it is

Types are purpose-built: Explore for read-only search across many files, Plan for architecture, plus general-purpose, code-reviewer, claude-code-guide. Each runs in isolation so its noise never touches your main thread.

Reach for it when

A question means reading across the codebase, or you have independent work to run at the same time. Launch several in one message and they run concurrently.

Try it

chat prompt
▸ Use an Explore subagent to find every call site
  of validateSplit and summarise the patterns.

# or fan three out at once, in one message:
▸ Spin up 3 subagents — one auditing auth, one the
  API routes, one the migrations — and report back.

Watch out

The subagent's report is not shown to you — the main agent has to relay what matters. To continue the same subagent with its memory intact you message it (its context is preserved); a fresh Agent call starts from zero.

Fan-out · several, hand-sequenced SDD

Subagent-Driven Development

A pattern, not a tool: take a written plan, dispatch one subagent per independent task in the current session, review each result, then move on.

What it is

The subagent-driven-development skill encodes it. Each task gets a clean worker; you (or Claude) act as the conductor between them — read the diff, then start the next. It keeps a big plan moving without one giant context.

Reach for it when

You have a plan whose tasks don't depend on each other and you want each built with a checkpoint in between — without leaving the session for a separate run.

Try it

chat prompt
▸ Execute this plan with subagent-driven development —
  one subagent per task, show me each diff before the next.

Watch out

There's no built-in orchestrator — it's sequenced turn by turn, so tasks must be genuinely independent. (This is exactly the pattern behind “lots of little changes at once.”)

Fan-out · many, programmed Workflow

Workflows — orchestration as code

A deterministic JavaScript program that drives dozens of subagents. Runs in the background; intermediate results live in the script, never in your context.

What it is

Building blocks: agent() spawns one, parallel() waits for all (a barrier), pipeline() streams items through stages with no barrier (the default), phase() groups progress. Because it's a script, control flow — loops, conditionals, fan-out — is exact and repeatable.

Reach for it when

The fan-out is big or repeated: audit every route for auth, migrate every call site, review across N dimensions and adversarially verify each finding.

Shape of a script

review-changes.workflow.js
const results = await pipeline(
  DIMENSIONS,
  // stage 1: review each dimension
  d => agent(d.prompt, { phase: 'Review', schema: FINDINGS }),
  // stage 2: verify findings as soon as each review lands
  r => parallel(r.findings.map(f => () =>
    agent(`Refute: ${f.title}`, { schema: VERDICT })))
);

Watch out

Opt-in only — say ultracode … or /effort ultracode, or run a saved /workflow. Up to 16 agents run at once (1,000 max per run), and there's no pausing for your input mid-run. It can burn a lot of tokens, so scale it to the ask.

Family two · drivers

What keeps it running

Driver · substrate + checklist Task

Task — the ground everything runs on

Two things wearing one name: a live progress checklist, and the background jobs that long-running work (including agents and workflows) actually runs as.

What it is

Tracking — a checklist you can watch: each step flips pending → in_progress → completed, so multi-step work shows where it is. Background execution — long jobs (a build, a subagent, a whole workflow) keep running and notify you on completion.

Reach for it when

Work has several visible steps worth tracking, or something slow should run without blocking the conversation.

In practice

task panel
✔ migrate config loader        completed
◐ wire up the check script      in progress
○ add /parallel command         pending

# background: a long build runs, you're pinged when it exits —
# no need to sit and watch it.

Watch out

When a tracked background job finishes, Claude is re-invoked automatically. Polling it with a tight loop just burns turns — let the notification do the work.

Driver · run until true Goal

Goal — a finish line, not a step count

/goal <condition> sets a completion condition. Claude keeps working turn after turn, and a small, fast model checks after each turn whether the condition is met — then stops.

What it is

You describe “done” instead of the path to it. The evaluator fires immediately and re-checks each turn; when it's satisfied, the run ends on its own.

Reach for it when

You can state the finish line crisply and want an unattended run straight to it — “make the suite green,” not “try these five fixes.”

Try it

slash command
/goal all tests in test/auth pass and typecheck is clean

# pair with auto effort for a truly hands-off run:
/effort auto

Watch out

Goal does not widen permissions — pair it with /effort auto for unattended work. The evaluator only sees what Claude surfaced in the transcript, not silent file reads, so make the evidence visible. Condition caps at ~4,000 characters.

Driver · run on a cadence Loop

Loop — do it again, on a clock

/loop [interval] [prompt or /command] re-runs on a fixed interval; omit the interval and Claude paces itself.

What it is

A recurring re-run of a prompt or slash command. Give it 5m and it's a fixed cadence; leave it off and Claude chooses when to wake based on what it's watching. For durable, session-independent runs, /schedule creates cloud routines on a cron.

Reach for it when

You're polling or babysitting — a deploy, a PR queue, a flaky check — and want a light touch back on it every so often.

Try it

slash command
/loop 5m /check-deploy        # fixed: every 5 minutes
/loop keep an eye on the PR queue  # self-paced
/schedule every weekday 9am, triage new issues

Watch out

/loop only fires while Claude Code is running — no catch-up if it's mid-task at fire time — and recurring loops expire after about 7 days. For runs that must survive your session, use /schedule.

Putting it together

They stack — one from each column

How wide does the work spread?

Agentone → SDDseveral, by hand → Workflowmany, by program

Same atom — an isolated worker — at three widths. Move right as the work gets bigger or more repetitive.

What tells it to keep going?

Taskbackground + tracking · Goaluntil a condition · Loopon a cadence

Not a progression — three different reasons work continues. Choose by whether “stop” is an event, a condition, or a clock.

Tie-back — your parallel-changes flow

This is the toolkit behind “many small changes at once”: SDD (or a Workflow) fans the changes into isolated worktrees, Task tracks them and runs the checks in the background, and a Goal like /goal every change's checks are green holds the bar until they all pass — with a Loop only if you want it re-checked on a schedule.
